Standard Test for Dialogs

This TPS is updated.Refer the new TPS at  //TestStand/WebPages/TestCases/StandardTest/GUI Testing checklist.docx


Test Description


Standard test to apply for a dialog.

Verify the FUNCTIONALITY of every action/option.

Test Procedure


 ------------Obsolette TPS----------------

  • Test that tip strips appear correctly strip when you move the mouse over list view fields that are too long to display without truncation.
  • Check title (and icon if appropriate)
  • Check tab order.
  • Check that dialog is opened with focus on an appropriate control
  • Check <Return> hot key for OK, <Esc> for cancel. If a button is selected, <Return> hot key presses the currently selected button.
  • Check that all changes are canceled by the cancel button
  • Check that all controls are validated when changing properties pages or when leaving the dialog with OK
  • Check alignment of controls
  • Verify all controls are themed. In a .NET app, check any non-.NET subdialogs.
  • Check that all combo boxes are the right type (dropdown vs. droplist)
  • Check that appropriate controls are dimmed.
  • Check that multi-line text controls have scroll bars
  • If applicable, test that edit controls with paths have the correct absolute path shown below in a non-editable text indicator. Verify that "." and ".." in path edit controls are collapsed in the absolute path.
  • Test in-place editing in list controls
  • Test that lack of needed user privileges dims all the appropriate controls
  • Test with large fonts
  • Check that changes are saved on ok and not on cancel.
  • Check that any modifications mark the associated file (if any) as modified
  • Verify that all expression fields use the expression edit control.
  • Verify that the expression edit controls do error checking correctly. To do this, make sure the expression edit control gives an appropriate error in the tooltip when the control does not have focus and also make sure a message dialog reports an appropriate error before the dialog closes. Note that some dialogs only report syntax errors, but for the dialogs that check expressions for evaluation errors, make sure the types they expect the expression to evaluate to are appropriate.
  • Check that expression controls that are one line high (i.e. look single-line), do not accept <Ctrl+Enter> for newlines.
  • Check that the context is appropriate for all expression edit controls. To do this, hit <Ctrl+Space> in the expression edit control to bring up the auto completion window or bring up the Expression Browser dialog. Examine the properties listed to make sure the context is appropriate.
  • Verify that every expression and floating point edit control supports the localized decimal point setting in the Station Options which may reference the Regional Settings in the control panel. To test, set the localized decimal point to comma, enter "1,2;3" in an expression, reset the localized decimal point to period, verify the expression contains "1.2,3". Then set the decimal point back to comma, and verify that the expression is "1,2;3".
  • If applicable, test that clicking the help button opens up the help file at an appropriate topic. Verify that <F1> opens the same topic. [The help button should be available in all non-trivial dialogs.]
  • If Read-Only is supported, test all controls in read-only mode. [Often, you can get read-only mode by opening dialogs while an execution is running.]
  • Check that the dialog doesn't leak any GDI resources. [To verify this, open the Task Manager and goto View->Select Columns and select the GDI Objects checkbox. Now you can see the GDI Objects for any process in the Task Manager. Now open and close the dialog multiple times (around 8-10) and make sure that the GDI Object usage is not steadily increasing for the Sequence Editor.]
  • Check that that the dialog doesn't leak memory.
  • Verify that the dialog doesn't use too many system resources. Launch two Sequence Editors and have each one display the dialog and verify you don't run out of system resources.
  • Check that the dialog has atl key shorcuts and verify that they work. Verify that there are no duplicate shortcuts. Verify that a control's shortcut does not work when the control is invisible. In MFC, shortcuts for invisible labels, buttons, and check boxes are still active. [If the keyboard shortcuts are not visible, hit <Alt> to activate them on Win2k and XP.]
    • Exception: "Cancel" buttons should not have alt-key shortcuts. This is because ESC should already produce the same functionality as the cancel button. There is no need to have two hotkeys for the same function. This confusion has come up a couple of times. See for example CAR 478257 and CAR 390604. A couple of notes:
      • Despite the above msdn blog post, we feel that "OK" should still have an accelerator because <ENTER> does not always mean "OK." The meaning of <ENTER> depends on which widget in the dialog has the focus. The agrees with the typical behavior of Microsoft Applications.
      • There are a number of places in our code that we still incorrectly have the alt-c accelerator for "Cancel." Do not create new CARs for existing features for this item alone. Removing an improper alt-c accelerator from a "Cancel" button should only be written as a CAR by itself for new features. Otherwise, do not worry about it unless you have something else to write a CAR about for the dialog. In that case, go ahead and add this as a clean-up item.
  • Verify that every context menu that you can bring up by right clicking can also be brought up with the keyboard using <Shift+F10> or the context menu key (the key to the left of the right Ctrl key). [This problem happens when you display a context menu in the WM_RBUTTONDOWN message instead of the WM_CONTEXTMENU message.]
  • Verify that buttons that display context menus display the menu at the button at not at the mouse cursor. Verify this by using the keyboard to click the button (press space when the button has focus).
