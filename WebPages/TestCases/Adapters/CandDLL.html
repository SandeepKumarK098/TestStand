Test Case Scenario
National Instruments Confidential

C\C++ DLL Adapter

Adapters



Test Description

 

This test is for testing the various features of the C/C++ DLL Adapter. You need to test using the SpecifyModule dialog as well as the Module panel in the Step Settings pane of the sequence editor. There are additional tests for testing the functionality of the Module panel itself.

Test Procedure

Note: As of TestStand 2010 Measurement Studio is no longer required for debugging or create/edit code operation.  You should run these tests on a machine without Measurement Studio to verify that it is no longer required.

  • C/C++ DLL Adapter Debugging
    • Setup
      1. Use DLLs from <TestStand Public>\Examples directory.
      2. (Optional) Use VS.NET 2005 to create a C DLL and/or C++ DLL with static entry points
      3. (Optional) Use CVI to create a C DLL with C entry points
    • Basic functionality
      1. Test with calling VS.NET DLL entry point
      2. Verify step into and step over work as expected
      3. Verify step into followed by step out stops on next step in sequence
      4. Verify step into followed by continue resumes executing the sequence
      5. Verify prompt if attempt to stop debugging or exit VS.NET
      6. Repeat above with VS.NET debugger already attached to SeqEdit.exe (specify SeqEdit as the debugging .exe for the VS.NET DLL)
      7. Verify CVI debugging functionality works properly (in CVI, specify SeqEdit as the debugging .exe for the CVI DLL)
      8. Verify no attempt is made to launch VS.NET debugger when calling VS.NET entry point
      9. Verify developing/debugging/rebuilding process works intuitively for VS.NET DLL steps
      10. Things to think about include switching of top level application and performance
    • Corner and failure cases
      1. Test with native debugging disabled in VS.NET
      2. Kill VSDebuggingController.exe at various stages of debugged execution
      3. Set various types of breakpoints at verious places (especially the first line) in the VS.NET DLL entry point and verify it is not removed
      4. Try multiple executions or threads calling different functions and calling the same functions
      5. Try stepping into a CVI-created function while debugging from VS.NET
      6. Try stepping into a release-compiled VS.NET DLL
      7. Move or rename the source file containing the VS.NET DLL entry point
      8. Test throwing an exception from code you stepped into
      9. Verify no debugging functionality with VS.NET 2002
  • Test Create/Edit Code in Visual Studio .NET for C/C++ DLL Adapter
    • Create Code
      1. Use the sequence file in //TestStand/Tests/TS Automated Tests/3.0/Interactive/CreateCode for testing.
      2. Verify that the browse buttons browse for the correct type of file and that the edit controls are correctly updated when a file is selected
      3. Test Create Code using various source, project, and solution files.
      4. Verify that if no solution file is provided, an appropriate solution is used (TS 3.0 Beta 2 requires a solution to be specified).
      5. Verify that if the solution file is already open in a Visual Studio environment, that environment is used for code generation.
      6. Verify that error messages are displayed if the files do not exist or are not the correct type.
      7. Verify that an error message is displayed if a function name is not provided on the module tab.
      8. Test functionality when the desired function already exists in source.
      9. Verify that a replace/insert above/insert below dialog is displayed and that the correct action is taken depending on the user's choice.
      10. Verify that the code template is correctly read and that any includes/imports, parameters types and names, and function body are transferred to the new function.
      11. Verify that the function name and parameters are updated in the module dialog after the function is created.
      12. Verify that create code for an array only puts the dimension size in the code for dimension sizes that are constant. For example, if you have a dimension with a size expression of Locals.foo, create code should omit the dimension size instead of using Locals.foo.
    • Edit Code
      1. Test Edit Code using various source, project, and solution files
      2. Verify that if no solution file is provided, an appropriate solution is used (TS 3.0 Beta 2 requires a solution to be specified).
      3. Verify that if the solution file is already open in a Visual Studio environment, that environment is used for code generation.
      4. Verify that an error message is displayed if the function does not exist in the source.
      5. Verify that the project and source are opened and that the cursor is moved to the first line of the correct function.
    • Verify Prototype (when not using Visual Studio integration only)
      1. Verify that Verify Prototype doesn't compare the dimension size of the first dimension in an array. For example, the C/C++ compiler treats parameters of type ary[][3], ary[2][3], and ary[3][3] as the same.
      2. Test Verify Prototype for structs and enums. You have to use the 'struct' and 'enum' keyword in the source code. Test both structs of type tsErrorDataType, which corresponds to the TestStand Error container, as well as structs you define.
  • Test 3.0 C/C++ DLL Adapter Features
    1. Type discovery: Using Visual Studio.NET, create DLLs that use various C++ datatypes. In SpecifyModule dialog, check if the functions/static methods appear in the dialog with the correct types. Use DLLs and projects in Tests\3.0\CppAdapter\CppDialogTest.
    2. Parameter passing: Test passing all supported MeasurementStudio datatypes using all parameter-passing variations: by-Value, by-Pointer, by-Reference, by-const-Pointer, by-const-reference. Don’t spend much time on this because this is part of the automated tests in Tests\3.0\CppAdapter. However, you should verify that you can configure steps to call some of these functions and that they run as expected.
    3. Verify that when using MStudio datatypes (for example CString) with a DLL that was not created with MeasurementStudio, we report useful warning message that explains how to correct the problem. Test this when running as well as when specifying module in dialog. [This warning is not provided with the Module Panel in the step settings pane.]
    4. Verify that if user specifies argument values that have incorrect type, we display a useful and accurate error message. For example, CNiScalarVector expects a 1-d array of Numbers (or Booleans).
    5. Test that specify module dialog and step settings pane recognizes functions and method names when typing in the Function combobox. Verify that namespaces are recognized. Try nesting namespaces.
    6. Test functions that have enum parameters. Verify that the enum name appears in the dialog and that we pass the correct values (dialog will not display possible enumeration values unless you have a type library because that information is not available form the DLL).
    7. Verify that "const" MStudio datatypes actually pass by value and do not modify the argument passed.
    8. Verify that "int" parameters appear differently from "long" parameters. Same with unsigned int, unsigned long.
    9. Verify that the function call in the specify module dialog and step settings pane looks correct with all parameter passing. For example, if pass-by-pointer then we add a "&" before the argument.
  • Standard Test for Adapters
  • Standard Test for Dialogs
  • CARs
    • Validate CARs 379312 and 379299.
      1. Create a custom step type with a default prototype that returns an integer.  In this step type’s return value parameter, set the default values of the ResultAct to 1.  Set the default Flags subproperty (not to be confused with the flags of a property) to have the 2 bit set (preserving the other bits).  For ResultAct and Flag properties, set the “Not Editable” flag.
      2. Note:  “Not Editable” is set for a subproperty by right-clicking on the property and selecting “Properties…” à “Advanced” à “Flags” à “Type Flags…” à and seting “PropFlags_NotEditable” for both the “Instance Default Flags” and “Flags Not Editable in Instances.”
      3. Create instances of each of these custom step types in the Sequence Editor and validate the following for the return values:
        1. “Set Error.Code” is checked.  (This field is controlled by the 0x2 bit of Flags.)
        2. “Result Action” is “If Value < 0 Set Error.Occurred to True.”
        3. The “Category”, “Type”, “Result Action”, and “Set Error.Code” fields should be read-only.  For other parameters these fields should not be read-only.
        4. Add a parameter to the prototype, then refresh the prototype, removing the parameter you just added.  Verify #1, #2, and #3 above.
        5. Change to a different prototype that returns void.  Then change to a third prototype that returns int.  Verify #1, #2, and #3 above.
      4. Create two new custom step types similar to the ones above, but in these make either the Flags subproperty or the ResultAct subpropery (but not both simultaneously) not editable.
        1. With just the Flags not editable:
          1. Verify that none of the fields “Category”, “Type”, or “Set Error.Code” can be modified.
          2. Verify that the “Result Action” field can be changed.
        2. With just the Result Action not editable:
          1. Verify that the “Category”, “Type,” and “Set Error.Code” fields can be modified.
          2. Verify that the “Result Action” field cannot be changed.
          3. Verify that when you change the “Category” to “Void” and then back to “Numeric” that the “Result Action” remains unchanged and not editable.
      5. Do some free-form testing.
